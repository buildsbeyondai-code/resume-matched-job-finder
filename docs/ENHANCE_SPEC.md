# Enhancement specification

Generated by Reuse-First Builder on 2026-11-06 11:45.

## Original requirement

Unattended (fully automatic) job auto-apply mode for the Resume-Matched Job Finder. While the app is running, a scheduler re-runs the user's saved job searches on a configurable interval, scores new postings against the resume, and automatically submits applications to every new job above a configurable minimum match score, using the existing company-site, Naukri and LinkedIn apply flows. It enforces a daily application cap, a per-company cooldown, quiet hours, skips duplicates and already-applied jobs, and has a one-click pause / kill switch. Every run is logged with proof screenshots; a daily summary shows what was applied, parked as Needs you, skipped and why. It never solves CAPTCHAs, never creates accounts, and parks anything uncertain for the user.

### Key user journeys (one per line)

J1 Turn on unattended mode: open Applications > Unattended. When nothing is set up yet (empty state), the page explains the feature and shows a Set up button. Choose which saved searches to include, the run interval, minimum match score, daily cap, company cooldown and quiet hours. Review a plain-language summary ('Up to 15 applications a day to jobs scoring 80 or more, every 60 min, not between 22:00 and 07:00'). Confirm. The status bar shows 'Running · next run 14:30'. Loading: the Save button shows a spinner and is disabled. Error: invalid fields are flagged inline with the fix, and nothing is saved.
J2 Scheduled run (no user present): the timer fires. The run is skipped and logged if mode is paused, it is quiet hours or the daily cap is reached. Otherwise the run re-runs each included saved search, scores postings and keeps those that are new and at or above the minimum score. It then drops duplicates, jobs already applied to, hidden jobs and companies still in cooldown, and applies to the rest one at a time through the existing company-site, then Naukri, then LinkedIn flows. Each job ends as Submitted (with a confirmation screenshot), Needs you (with a reason) or Skipped (with a reason).
J3 Pause or kill: from any view, one click on Pause auto-apply stops the scheduler and aborts any application in progress before its next form action. The aborted job is parked as Needs you ('Interrupted, check whether it was submitted'). The status shows 'Paused'. Resume asks for confirmation and restarts the schedule.
J4 Daily summary: open Today (or pick a past date) to see counts and lists of Applied, Needs you and Skipped, each with its reason, company, score, source and time. Open the proof screenshot for any Submitted job. Empty: 'No unattended runs on this day'. Loading: skeleton rows. Error: 'Couldn't load summary' with a Retry button.
J5 Resolve Needs you: from the summary, open a parked job. Answer the missing required question (saved for future runs, the same as today), open the posting to apply by hand, or dismiss it. The status updates without a page reload.
J6 Run log: a list of runs showing start and end time, trigger, searches, counts, source errors and per-job outcomes. Empty, loading and error states are the same as in J4.

### MUST-have features (one per line)

M1 Unattended settings, stored in SQLite and off by default: included saved searches, interval (15 to 1440 min), minimum match score (0 to 100), daily cap (1 to 100), company cooldown (0 to 365 days) and quiet hours (local start and end time; may span midnight). The user must explicitly confirm before the first enable.
M2 In-process scheduler: runs only while the app is running and never runs two at once (a run that is still going makes the next tick be logged as 'skipped: previous run active'). After the app was closed, at most one catch-up run happens on start.
M3 Each run reuses the existing search.py and matching.py to re-run the included saved searches and score postings. It selects only postings that are new since that search last ran and score at or above the minimum.
M4 Eligibility guards, each logged as a Skipped reason: duplicate (existing dedupe key), already applied (any existing Applications status other than not started), hidden by the user, company in cooldown (manual and automatic applications both count), daily cap reached (the job is deferred and reconsidered in a later run, not discarded).
M5 Quiet hours: no run starts and no Submit is pressed during quiet hours. A run in progress when quiet hours begin stops before the next job.
M6 Applications go through the existing apply flows unchanged (company site first, then Naukri, then LinkedIn). A job counts as Submitted only after the existing confirmation check passes and its screenshot is saved.
M7 Never guess. Anything uncertain is parked as Needs you with a specific reason: CAPTCHA, sign-in wall, account-creation prompt, unanswered required question, no portal match with similarity of 0.6 or more, no confirmation seen, unexpected page or timeout. The app never solves CAPTCHAs, never creates accounts and never invents answers.
M8 Pause / kill switch: one click, visible on every view, takes effect within 5 s, aborts the application in progress before its next form action, and stays paused after a restart.
M9 No double applying: an 'attempting' record is written before Submit is pressed. After a crash or kill, such a job becomes Needs you ('Interrupted, check') and is never retried automatically.
M10 Run log: every run is stored with start and end time, trigger, searches, per-source errors, per-job outcome and reason, and screenshot path.
M11 Daily summary view (J4), with Applied, Needs you and Skipped lists and reasons, plus links to proof screenshots.
M12 If one source fails, the run continues with the other sources and logs the failure.
M13 New views (settings, status bar, summary, run log) have empty, loading, error, success and disabled states, in light and dark themes, and reflow at 320 px.
M14 Existing rules hold: outbound requests only to config.ALLOWED_HOSTS through the existing HTTP or apply paths; resume text is never sent anywhere except the application form being submitted; no innerHTML; decisions recorded in docs/DECISIONS.md.
M15 Existing features and the full existing test suite (python3 -m unittest discover -s tests -t .) keep passing unchanged.

### Acceptance criteria: Given / When / Then (one per line)

M1: Given a fresh upgrade, when the user opens Applications > Unattended, then mode is Off and the empty state is shown. Given interval = 5, when the user saves, then an inline error says 'Interval must be 15-1440 minutes' and nothing is saved. Given valid settings, when the user confirms, then they are saved and the status shows 'Running · next run HH:MM'.
M2: Given a run is still in progress, when the next interval tick fires, then no second run starts and the log shows 'skipped: previous run active'. Given the app was closed for 3 intervals, when it starts, then exactly one catch-up run happens.
M3: Given a saved search returns 10 postings, 4 of them new and 2 of those new ones scoring at or above the minimum of 80, when a run executes, then exactly those 2 become application candidates.
M4: Given a candidate the user already applied to by hand, when a run executes, then it is Skipped with 'already applied'. Given a company applied to 3 days ago with a 30-day cooldown, then its jobs are Skipped with 'company cooldown until <date>'. Given the cap of 15 is reached, then the remaining candidates are 'deferred: daily cap' and are considered again the next day.
M5: Given quiet hours of 22:00-07:00 and a local time of 23:10, when the timer fires, then no run starts and the log shows 'skipped: quiet hours'. Given a run in progress at 21:59, when 22:00 passes, then no further Submit is pressed.
M6: Given an eligible company-site job, when it is applied to, then the status becomes Submitted only once the confirmation page is detected and a screenshot file exists. Given no confirmation is detected, then the status is Needs you ('no confirmation seen').
M7: Given a form shows a CAPTCHA, sign-in wall or 'create account' prompt, when unattended mode reaches it, then nothing is typed into that element, nothing is submitted, and the job is Needs you with that exact reason.
M8: Given an application is mid-form, when the user clicks Pause, then within 5 s no further form action happens, the job is Needs you ('Interrupted, check'), the status shows Paused, and after restarting the app it is still Paused.
M9: Given the process is killed after the 'attempting' record but before confirmation, when the app restarts, then that job is Needs you ('Interrupted, check') and no run applies to it again.
M10: Given a finished run, when the user opens the Run log, then the entry shows start and end time, trigger, searches, per-source errors and every job's outcome and reason, and each Submitted job links to an existing screenshot.
M11: Given today has 3 Submitted, 2 Needs you and 5 Skipped jobs, when the user opens Today, then the counts read 3/2/5 and each row shows its reason. Given a day with no runs, then the empty state is shown. Given the summary API fails, then an error with Retry is shown, and Retry reloads the summary.
M12: Given one source returns an HTTP 500 during a run, when the run finishes, then candidates from the other sources were still processed and the log names the failed source.
M13: Given each new view, when it is rendered at 320 px in light and in dark theme, then there is no horizontal scrolling, all states are reachable in tests, and the contrast checks in tests/test_ui_static.py pass.
M14: Given a full unattended run under test, when outbound requests are recorded, then every host is in config.ALLOWED_HOSTS or is the apply target, and no request outside the form submission being made contains resume text.
M15: Given the enhancement is merged, when python3 -m unittest discover -s tests -t . runs, then every existing test passes and the new tests trace to M1-M14.
