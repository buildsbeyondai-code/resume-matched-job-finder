# Enhancement specification

Generated by Requirement Reuse Analyzer on 2026-11-06 01:21.

## Original requirement

100% auto apply for the Resume-Matched Job Finder (enhancement). When I press Apply or Auto apply, every job must be applied for automatically, without me visiting any website, in this order:
1) the company's own website (already built: Adzuna /land/ad/ redirect, then the company's Greenhouse/Lever/SmartRecruiters/Ashby/Workable board);
2) if the company has no website application, apply on Naukri, then LinkedIn (Easy Apply), signed in once in the app's browser. Find the same job with the portal's own search, match company and title, click Apply/Easy Apply, fill every step (Naukri chat-style question drawer with contenteditable answers and radio chips; LinkedIn Easy Apply dialog with Next/Review/Submit application), submit and verify the confirmation ("Your application was sent", "You have successfully applied"). Naukri one-click Apply (no questions) counts as submitted when the confirmation appears. Prefer a portal's "Apply on company site" button when shown.
3) Portals are opt-in in Settings (Naukri, LinkedIn; both on by default), used only as the last resort, one job at a time, with a configurable pause between portal applications (rate limit, default 20 s). Never bypass CAPTCHA, never create accounts, never apply through Adzuna; sign-in walls park the job as "Needs you".
All answers come from resume_details.md; only required questions it can't answer are asked once (merged across jobs) and saved back.
Work already started but not wired: app/portals.py (portal search URLs, result matching) and apply.py changes (dialog-scoped scanner, contenteditable fields, chat "Save" as next, COMPANY_SITE_RE, _find_form(force)). Finish and wire them (_company_site portal fallback, applied-on-click detection, portal pause in autoapply.Runner, fallback_portals setting + Settings UI, Applications tab shows "via Naukri/LinkedIn").
Testing: 100% line and branch coverage for app/apply.py, autoapply.py, details.py, direct.py and portals.py (tools/coverage.sh gate) with integrated end-to-end tests using real Chromium against local fake Naukri and LinkedIn pages added to tests/fake_careers.py (never the real sites). All existing tests keep passing.

### Key user journeys (one per line)

J1 Company site first: user presses Apply on a job → app finds the company's own application (Adzuna /land/ad/ redirect, then Greenhouse/Lever/SmartRecruiters/Ashby/Workable board) → fills, submits, verifies → Applications shows "Applied via company site". (Existing behaviour, unchanged.)
J2 Naukri fallback: no company-site application → Naukri enabled and signed in → app searches Naukri, matches company and title → if "Apply on company site" is shown, follows it and runs J1's form filler; otherwise clicks Apply, answers the chat drawer (contenteditable answers, radio chips, Save), verifies "You have successfully applied" → Applications shows "Applied via Naukri" with a confirmation screenshot.
J3 Naukri one-click: Apply with no questions → confirmation appears → counted as submitted.
J4 LinkedIn fallback: not on Naukri, or Naukri disabled or no match → app searches LinkedIn, matches the job → prefers "Apply on company site"; otherwise opens Easy Apply, fills each step (Next/Review/Submit application), verifies "Your application was sent" → "Applied via LinkedIn".
J5 Batch Auto apply: user presses Auto apply for N jobs → company sites first; portal applications run one at a time with the configured pause (default 20 s). A visible countdown and progress show for each job, and the user can cancel.
J6 Missing answers: required portal questions that resume_details.md can't answer → job parked → questions merged across jobs and asked once in Applications → answers saved to resume_details.md → parked jobs resume.
J7 Blocked: sign-in wall, CAPTCHA, no portal match, or portals disabled → job parked as "Needs you" (reason shown) or "No company website". Nothing is guessed or bypassed.
J8 Settings: user turns Naukri/LinkedIn on or off and sets the portal pause. Values are validated and persist.
UI states for each journey: empty (no applications yet / no pending questions), loading (searching portal, filling step x of y, pause countdown), error (portal unreachable, confirmation not found, browser not installed), partial (some jobs applied, some parked), success.

### Acceptance criteria: Given / When / Then (one per line)

M1 Given a job whose company has no site application and Naukri is enabled, when the user presses Apply, then the company site is tried first and the Naukri fallback runs only after that attempt reports no application (asserted by call order in tests)
M2 Given a portal result that shows "Apply on company site", when the job is applied, then the app follows that link, submits the company form and records "via company site"
M3 Given fake Naukri search results with one matching and two non-matching company/title rows, when the job is applied, then only the matching row is opened. Given no matching row, then LinkedIn is tried next, and if LinkedIn has no match either, the job is parked as "Needs you: not found on portals".
M4 Given the fake Naukri chat drawer with text and radio-chip questions answerable from resume_details.md, when Apply runs, then every answer is filled, Save is pressed per step and the status becomes Applied after "You have successfully applied" appears. Given a one-click job, then the status becomes Applied once the confirmation appears.
M5 Given the fake LinkedIn Easy Apply dialog with three steps, when Apply runs, then each step is filled, Next/Review/Submit application are pressed in order and the status becomes Applied after "Your application was sent"
M6 Given a portal whose Submit leads to no confirmation text, when Apply runs, then the status is "Needs you: confirmation not found", not Applied. Given an Applied job, then a confirmation screenshot file exists.
M7 Given a fresh database, when Settings opens, then Naukri and LinkedIn are on and the pause is 20 s. Given the user saves Naukri off and a pause of 45, when the app restarts, then those values persist. Given a pause outside 0–600 or non-numeric, then an inline error appears and nothing is saved.
M8 Given 3 portal jobs and a pause of 2 s in tests, when Auto apply runs, then the portal applications never overlap and successive starts are ≥2 s apart
M9 Given the fake portal shows a sign-in wall or CAPTCHA, when Apply runs, then no click happens on it, the job is "Needs you" with the reason, and the run continues with the next job. Given an Adzuna-only job with portals disabled, then the status is "No company website" and Adzuna is never posted to.
M10 Given two jobs that ask the same unanswered required question, when Auto apply runs, then the question is listed once in Applications. When the user answers it, the answer is appended to resume_details.md and both jobs resume.
M11 Given applications made via company site, Naukri and LinkedIn, when the Applications tab opens, then each row shows the matching "via …" label. Given no applications, then the empty-state message shows.
M12 Given the test suite, when tools/coverage.sh runs, then it exits 0 only if the five modules report 100% line and branch coverage, and the network guard confirms no request left 127.0.0.1
M13 Given the enhancement is merged, when python3 -m unittest discover -s tests and tests/e2e_browser.py run, then all previously existing tests pass unchanged

### Memory / CPU limits

No new Python runtime dependencies beyond Playwright (already used)

### Reliability and recovery

Each job is processed at most once per run (idempotent: an Applied job is never re-submitted, keyed by job id + channel)
A crash or cancel mid-run leaves no job wrongly marked Applied. On restart, an in-progress job returns to Queued.
A failure on one job (timeout, selector missing, portal error) parks that job and the run continues
Step timeouts are 30 s per portal step, with at most 1 retry for navigation errors and no retry after Submit has been pressed

### Security

Server binds to 127.0.0.1 only. Outbound hosts go through config.ALLOWED_HOSTS, now extended with naukri.com and linkedin.com for the browser only.
No passwords or tokens are stored by the app. Portal sessions exist only in the app-owned Chromium profile directory (permissions 0700).
Resume text and answers go only to the employer/portal form being submitted, never to any other service
No CAPTCHA bypass, no account creation, no Adzuna apply path (each enforced by a test)
No innerHTML in new UI code. All portal-derived text is rendered as textContent.
Tests use only local fake pages, and a network guard fails the test on any non-loopback request.

### Accessibility and UI states

WCAG 2.2 AA for all new UI (Settings portal toggles, pause input, "via" labels, Needs-you reasons, pause countdown)
Text contrast ≥4.5:1, non-text and focus indicators ≥3:1, verified by tests/test_ui_static.py in both light and dark themes (theme parity: every new token is defined for both)
The whole flow can be done by keyboard. Focus is visible (≥2 px outline) and the focus order is logical. Target size is ≥24×24 CSS px (2.5.8).
Toggles are native checkboxes/switches with <label>. The pause input has a label, a unit ("seconds"), min/max, and an inline error linked via aria-describedby.
Status changes (Applying via Naukri, pause countdown, Applied, Needs you) are announced via an aria-live="polite" region. Errors use role="alert".
The page reflows at 320 px with no horizontal scroll and works at 200% zoom/text spacing
Empty, loading, error and partial states each have a visible text message, not colour alone
ISO 9241-110: the current channel and step are always shown (self-descriptiveness), Cancel is available at every stage (controllability), and Needs-you reasons say what to do next (error tolerance)
