# Decisions (non-interactive build; every default is reversible)

| ID | Decision | Why / how to reverse |
|---|---|---|
| D1 | Python standard library only (http.server, sqlite3, zipfile, zlib, urllib); no Flask, pypdf or pytest | Installing packages was blocked in the build environment. This also meets the "setup ≤ 5 min" goal. To reverse, swap in Flask and pypdf behind the same modules. |
| D2 | Our own minimal PDF text extractor (FlateDecode + Tj/TJ operators, hex strings) | No PDF library was available. **Limitation:** PDFs using CID or Type0 fonts without readable strings, and scanned PDFs, give a clear "no readable text" error that suggests a DOCX. Upgrade path: pypdf. |
| D3 | Tests use `unittest`. "E2E" means API-level journeys over real HTTP with a mocked network. No real browser tests | Neither a browser nor Playwright was installable. The browser-based UI gate items are marked UNVERIFIED. |
| D4 | Sources: Greenhouse, Lever and SmartRecruiters public board APIs plus Adzuna (key from env) | These are official public or licensed APIs, so no scraping (M3). |
| D5 | Default boards: Bosch and Visa (SmartRecruiters), Cloudflare (Greenhouse), Palantir (Lever) | Most of the requested MNCs (Microsoft, Google, Amazon and others) do not publish public ATS board APIs. They are reached through Adzuna plus the Companies filter, and the target-company list sits in Settings. Boards can be edited in Settings. Visa returned 0 postings in the live check. |
| D6 | Match score = 70 × skill coverage + 15 × title similarity + 15 × seniority fit | Simple, explainable and local. Seniority defaults to Mid (3-7 years). |
| D7 | Uploading saves the extracted profile right away, and the user then edits and saves it | One fewer step. The edit form opens with focus on Skills. |
| D8 | Duplicate key = normalised company + title + first location token | Meets M5. It can miss duplicates where companies are named differently across sources. |
| D9 | Hide uses undo (no confirmation). Delete-all uses a named confirmation dialog. Removing a source uses a confirm prompt | UEUIS §11. |
| D10 | Optional features: O2 CSV export is built. O1 (LLM explanation) and O3 (scheduled refresh) are not built | Time budget. Refresh is manual, as the spec chose. |
| D11 | Cache identical source URLs for 1 h. Prune postings older than 60 days that are not saved | Spec limits. |
| D12 | Palette "Pine & Paper" (light) and "Pine Night" (dark), with solid pine-green primary #1d6b57 / #62c3a6 | The app's own identity, deliberately not generic blue. |
| D13 | Writes require a local Host header and Origin (blocks DNS rebinding and cross-site requests). A strict CSP is set | Security for a local server. |
| D14 | A source that needs an API key that was never set (Adzuna) is shown as "Skipped (no API key)" and is not counted as failed | It is optional, so a missing key should not show the "results may be incomplete" warning on every search. Real failures (timeouts, HTTP errors) still show the warning. |
| D15 | With no resume, jobs are ranked by how well they match the search terms (title hits weigh most; floor 40) | Resume-based scores were ~4/100 without a resume, so the default 40 minimum hid every result. |
| D16 | The job title is a link to the posting, with an "Open job" button and the full link in Details | Users could not find the old text-style "View posting" link; the title only expanded details. |
| D17 | **Apply** opens the application in a visible Playwright Chromium window (persistent profile `data/browser-profile`) and fills it from `resume_details.md` in the JOB SEARCH folder (`RMJF_JOBSEARCH_DIR`) | The user asked for one-click applications. A visible window lets them sign in, solve CAPTCHAs and review. Playwright is an optional dependency; the rest of the app stays standard-library only. |
| D18 | The assistant never clicks the final Submit | Submitting is irreversible and sent in the user's name. The user reviews the filled form and submits it in the browser. |
| D19 | Only required fields that the details file can't answer are asked, in the app's Apply dialog; answers are saved to `resume_details.md` (recognised questions under a canonical field such as "Visa sponsorship", others under the question text) | The user asked never to be asked the same thing twice. Canonical fields let differently worded questions reuse one answer. Optional unknown fields are left blank. |
| D20 | Filling an employer's application form is an intended exception to "never send resume text out" | The user explicitly asks the app to enter their details on the employer's site. Only the details file values and the resume file are entered, and only on the job's own https page. |
| D21 | Skill score = job-side coverage where matching 60% of a posting's skills (at least 3) is full marks; resume skills the job doesn't mention cost nothing | The user said a job should not be expected to use every resume skill, and nobody has every skill a posting lists. The floor of 3 stops a one-skill snippet from scoring 100. |
| D22 | PDFs are read with optional `pypdf` first, then the built-in reader; text that is mostly glyph codes is rejected with a clear message | The user's resume uses CID fonts that the built-in reader turned into garbage, which silently produced an empty profile. |
| D23 | Job skills are re-detected at scoring time | Postings stored before a vocabulary update would otherwise keep their old skill lists. |
| D24 | Apply never applies through an aggregator (Adzuna). It follows the aggregator's company-site redirect (`/land/ad/`). Failing that, it finds the posting on the company's own Greenhouse/Lever/SmartRecruiters/Ashby/Workable board (title match ≥ 0.6). Otherwise it opens a careers web search and stops. | The user wants every application to go to the employer's own website. Ashby and Workable public APIs were added to the allow-list for this lookup only. |
| D25 | **Auto apply** submits applications end to end: it finds the company form, fills it, steps through Next pages, presses Submit and requires a confirmation page. Proof screenshots are kept in `data/applications/`. Supersedes D18. | The user asked for 100% automatic applications with no manual website visits. A batch is confirmed once in a dialog (max 25 jobs). Jobs already submitted are never applied for twice. |
| D26 | Auto apply never bypasses a CAPTCHA, never creates accounts and never applies through an aggregator. Those jobs are parked as "Needs you" or "No company website", with Retry and "I applied" actions. | Bypassing CAPTCHAs breaks site terms. A guessed account or answer submitted in the user's name can't be taken back. |
| D27 | Required questions from all queued jobs are merged into one "Answer once" form. Answers are saved to resume_details.md, and every job they unblock resumes automatically. | This keeps the "ask only what's missing, once" rule across a batch. |
| D28 | Test gate: 100% line and branch coverage for app/apply.py, autoapply.py, details.py and direct.py, and every apply/auto-apply route in server.py (`tools/coverage.sh`). The end-to-end test drives real Chromium against a local fake careers web (`tests/fake_careers.py`), never against real employers. | The user asked for 100% integrated test coverage. Real sites can't be used for tests, because a test would submit real applications. |
| D29 | **Job-portal fallback (Naukri, then LinkedIn).** It runs only for aggregator jobs, after the company-site lookup (Adzuna `/land/ad/` link, then the company's own board) finds nothing. The portal's own search runs in the app's browser. A result counts only when the normalised company appears on the result card and the title similarity is ≥ 0.6. If several results match, the order is: in the job's city, then newest, then closest title. On the portal, "Apply on company site" is preferred, and the job is then recorded as "via company site". | User spec (2026-11-06). The portals' terms restrict automation, so they are opt-in in Settings (both on by default, as specified) and used only as the last resort. To reverse, untick both portals in Settings. |
| D30 | Portal hosts are listed in `config.BROWSER_PORTAL_HOSTS` and **not** in `ALLOWED_HOSTS` | The spec said "extend ALLOWED_HOSTS for the browser only". `ALLOWED_HOSTS` is the allow-list of `sources.http_get`, so adding the portals there would let server-side code fetch them. A separate set keeps them reachable by the browser only (a unit test checks the two sets don't overlap). |
| D31 | Rate limit: the configured pause (default 20 s, allowed 5–600 s) runs **once per job**, before its first portal visit, and counts from when the previous portal job finished. Portal work is always serial, because a single browser thread runs it. | "Pause between portal applications". Searching Naukri and then LinkedIn for the same job doesn't add a second pause. Tests store a 2 s pause directly in SQLite; the UI and API accept only 5–600. |
| D32 | A job is counted as Applied only when confirmation text appears that wasn't on the page before (`apply.confirmed`). A Naukri one-click Apply counts once "You have successfully applied" appears. If a portal shows no confirmation after **Submit**, the job is parked as "Needs you: Confirmation not found", and Submit is never pressed twice. | M6. A wrong "Applied" status is worse than asking the user to check. |
| D33 | A sign-in wall (password field, or a `/login`, `/authwall` or `/checkpoint` URL) or a CAPTCHA on any portal page parks the job as "Needs you" with the next step. Nothing on the wall is clicked. A missing match on every enabled portal gives "Needs you: Not found on portals". With portals off, the job stays "No company website". | M9 and M3. These are the spec's exact status texts. |
| D34 | **Deviation:** after a restart, a job that was running is still marked "failed: Interrupted … Press Retry", not re-queued | The spec asked for "returns to Queued", but M13 requires the existing tests to pass unchanged, and one of them asserts the current behaviour. Auto-resuming would also send applications in the user's name without them present. Retry re-queues the job with one click. |
| D35 | In test mode (`RMJF_ALLOW_LOCAL_HTTP` / `config.ALLOW_LOCAL_HTTP`), a portal is used only if its base URL is loopback | Test mode is already the "local fakes only" switch. It means the existing end-to-end test, which runs with the default "portals on", can never reach the real Naukri or LinkedIn. A browser-level network guard in the portal end-to-end test also aborts and records any non-loopback request. |
| D36 | Portal sign-in status comes from the browser profile's session cookies (`nauk_at` for Naukri, `li_at` for LinkedIn), read only when the user selects "Check sign-in status". A portal sign-in wall marks the portal "not signed in". Sign-in and check are refused (409) while auto apply holds the browser. | No passwords are stored (spec). The cookie names are the portals' current session cookies. If they change, the status shows "not signed in", but applying still works and a real wall still parks the job. |
| D37 | Cancel: queued jobs become "Cancelled" (Retry re-queues them). The running job stops at its next step or during the pause, and never between pressing Submit and checking the confirmation. | J5 and the reliability rule "a cancel leaves no job wrongly marked Applied". |
| D38 | O1 (per-run cap on portal applications) is not built | The spec default is 0 (unlimited), the batch is already capped at 25 jobs, and the pause limits the rate. Time budget. |
| D39 | The channel is stored as `channel` (company / naukri / linkedin) inside the existing applications JSON, so no new SQL column is needed. Rows from before this change have no channel and show as "via company site". The new settings fall back to `config.DEFAULTS`, so existing databases need no migration step. | The application data is already a JSON document. The migration test opens an old-schema database. |
| D40 | **Unattended auto-apply (2026-11-06).** Settings and state are stored as one JSON value under the `unattended` key of the existing `settings` table (off by default; `enabled`, `paused` and the guard values). The run log uses two new tables, `ua_runs` and `ua_jobs`, created with `CREATE TABLE IF NOT EXISTS` on start. | This is an additive, idempotent migration, and existing data is untouched (test_migration_of_an_existing_install). To reverse, turn the mode off, or drop the two tables and the settings row. |
| D41 | A "saved search" is each distinct search the user has run: one row per distinct `searches.params`. Its id is the first 12 hex characters of the SHA-1 of the params JSON. The 50 most recent are listed, and each has its own switch (S5). None is on by default. | The app had no separate "saved search" entity, and the spec's default is "only searches I switch on individually". The id is stable across restarts. |
| D42 | "New since that search last ran" = posting keys in this run's result that were not in the previous stored result of the same params. Only these, at or above the minimum score, become candidates (M3). | This reuses the existing "New" chip logic (`db.last_search`). A skipped run doesn't run the search, so nothing is lost. |
| D43 | **Dry-run preview first.** When the mode is turned on for the first time, a preview run starts right away. Until a preview has finished, every run is a preview: it logs "dry run: would apply" and submits nothing. Preview and cap-deferred jobs are reconsidered in the next run. A **Dry run** button can be pressed at any time. | Spec input "dry-run preview before the first real run: yes". It is also safer, because the user sees what would be sent before anything is. |
| D44 | Schedule: next run = last tick + interval. The timer thread sleeps until then (at most 300 s per wait, so a clock change is noticed), and settings changes wake it. A tick more than 120 s late is logged as "catch-up". Because the tick moves `last_tick` to now, a long downtime produces exactly one catch-up run (M2). Ticks are also logged while paused or in quiet hours, as "skipped: …". | A single timer and no busy polling (CPU limit). |
| D45 | Runs never overlap: a tick that finds the run thread alive is logged as "skipped: previous run active". Applications reuse `autoapply.Runner.run_one`, so they go through the single apply-browser thread (at most one browser session). If a manual Auto apply batch is running, the unattended jobs are deferred. | M2 and the one-browser limit. |
| D46 | Guards, in order: duplicate (the same dedupe key seen earlier in this run), already applied (Submitted or "I applied"), already in Applications with another status (shown with that status, e.g. "needs you"), hidden by you, company cooldown (normalised company name; manual and automatic applications both count), no https application link. The daily cap counts **unattended submissions** on the local calendar day. When it is reached, the remaining jobs are "deferred: daily cap". | M4. Counting only unattended submissions keeps hand-applied jobs from blocking the automation. Hand-applied jobs still drive the company cooldown. |
| D47 | Pause, quiet hours and Off abort the application in progress through the auto-apply hooks, which are checked before every form action and click. The job becomes Needs you: "Interrupted, check whether it was submitted". The pause is persisted. Resume needs `confirm: true` (UI dialog), and the schedule restarts one interval after resume. | M5 and M8. The hooks already guard every Playwright action, so the existing apply flows are unchanged. |
| D48 | Crash safety: an `attempting` row is committed before `run_one` starts. On start, every `attempting` row and its application become Needs you ("Interrupted…"). Because the job is then in Applications, the "already in Applications" guard means it is never retried automatically. | M9: zero duplicate submissions. |
| D49 | A job counts as Submitted only when the existing flow reports `submitted` **and** the proof screenshot file exists. That file is chmod 0600 (its folder 0700). Every other result maps to Needs you with a specific reason. Nothing is guessed. | M6 and M7. The CAPTCHA, sign-in and account walls are detected by the existing flows (D26 and D33). |
| D50 | S1: after 3 run-level errors in a row (every saved search failed, or an exception), the mode pauses itself, and a banner explains why. Job-level Needs you outcomes don't count. | Spec default of 3. |
| D51 | Optional features: O1 is built as an in-page live-region announcement when the open Needs you count rises (no system notification permission is asked for). O2 is built as summary CSV export, with formula-injection quoting. O3 (screenshot expiry) is **not built**: the spec default is 0, which means keep forever. | Time budget, and the spec defaults. |
| D53 | Unattended runs re-run each saved search with `search.start(..., fresh=True)`. This bypasses the 1 h HTTP cache and still goes through `sources.http_get` and `ALLOWED_HOSTS`. | Otherwise a run within an hour of a manual search would see the cached result and find nothing new. One request per source per interval (minimum 15 min) stays polite. |
| D52 | The run log and summary hold only job, company, score, source, status and reason. They never hold form values or resume text. The screenshot path stays on the server, and the UI uses `/api/applications/<key>/proof`. | Spec security section. |
| D54 | **Claude Opus 5.5 answers the questions resume_details.md can't (2026-11-06).** It runs after the details file has filled the form, sends only the unanswered required questions (with options), the job, resume_details.md and the resume text, makes one call per form step, and asks each question once. Claude is told to answer only from those facts, to copy option text exactly, to decline voluntary self-identification, and to return null for salary, notice period, start date, relocation, visa or work authorisation not stated, legal consents and references. An answer that fits none of the field's options (or a checkbox answer that is neither yes nor no) is still asked. A Claude error or timeout (180 s) leaves every question asked, with the reason shown. Claude's answers are shown (label, value, basis) in Applications and the Apply dialog, and are **not** saved to resume_details.md: only the user's own answers are. Never used on sign-in forms. | User request: "use AI Claude Opus 5.5 while applying". This changes the earlier rule "never send resume text out": it is sent to Anthropic only while the Settings switch "AI answers" is on (default on, as requested), and the setting's text says so. Claude is reached through the Claude Code CLI (`claude -p --model claude-opus-5-5 --tools "" --json-schema …`, $1 cap per call) because it uses the user's existing Claude sign-in with no API key. In test mode only a fake CLI (`RMJF_CLAUDE_BIN`) runs. To reverse, untick "AI answers". |
